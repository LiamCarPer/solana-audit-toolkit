# SAT-004: PDA Seed Mismatch Between IDL Declaration and Runtime Derivation

**Severity:** HIGH

## Description

The Anchor IDL declares PDA seeds for an account that differ from the seeds used in the `#[account(seeds = ...)]` constraint at runtime. The IDL declares seeds `[b"vault", authority.key().as_ref()]` for the `vault` account, but the code-level derivation diverges — for example, a different seed order, different seed bytes, or a complete omission of the authority component.

The vulnerable code pattern:

```rust
// IDL declaration (idl.json):
// { "name": "vault", "seeds": [{"kind": "const", "value": [118, 97, 117, 108, 116]},
//                               {"kind": "account", "path": "authority"}] }

#[derive(Accounts)]
pub struct Deposit<'info> {
    // BUG: seeds reversed — IDL declares [b"vault", authority]
    #[account(
        mut,
        seeds = [authority.key().as_ref(), b"vault"],
        bump = vault.bump
    )]
    pub vault: Account<'info, Vault>,
    pub authority: Signer<'info>,
}
```

The IDL says the PDA is derived from `[b"vault", authority]`, but the program derives it from `[authority, b"vault"]`. These are different program addresses: `Pubkey::find_program_address` is order-sensitive and byte-sensitive. Every tool, indexer, and client library that trusts the IDL will derive an address the program will never accept — and the address the program actually uses is one nobody can predict from the IDL.

The same class of bug covers:
- **Seed omission** — IDL declares `[b"vault", authority]`, code uses `[b"vault"]` (a global, user-agnostic PDA).
- **Seed byte divergence** — a string literal (`b"VAULT"` vs `b"vault"`) or a serialized key that does not match the IDL's declared bytes.
- **Seed order swap** — identical bytes in a different order, as above.

The result is the same in every variant: the address the program reads and writes is not the address the IDL (and therefore every external integrator) expects.

## Exploit Scenario

1. Alice deploys a vault program. The IDL (generated by `anchor build` before a refactor) declares the vault PDA as `find_program_address([b"vault", authority])` — scoped to each depositor.
2. A refactor swaps the seed order in `#[account(seeds = ...)]`, or drops the authority seed, but the deployed IDL is never regenerated. The on-chain program now derives a **different** address for the same logical account.
3. Bob calls `deposit`. The program derives its PDA at the *code-level* address (e.g. global `[b"vault"]`) and writes Alice's funds there.
4. Any other user — or Bob himself — can call `withdraw` and supply an account at the *IDL-declared* address, or simply pass an attacker-derived account at the code-level address. Since the seed is global and not user-scoped, the program treats the account as valid and transfers funds out of a state it believes belongs to the caller.
5. Even without an active attacker, integration is broken: clients deriving `[b"vault", authority]` from the IDL point at an address the program never reads, so funds can be locked in the code-level PDA forever — or read/written at the wrong address entirely, causing state confusion across users.

The core danger: the IDL and the source each look internally consistent when reviewed alone. The vulnerability only appears when the runtime derivation is compared against the IDL declaration — exactly the comparison `sat` performs.

## Identification via Static Analysis

The `sat analyze src` command (cross-referenced against the IDL via `sat analyze idl`) detects this vulnerability automatically:

```
$ sat analyze src programs/vault/

#3 [HIGH] PDA Seed Mismatch: `deposit` derives `vault` from seeds per IDL but
          `Deposit::vault` has no `seeds` constraint
  📍 programs/vault/src/instructions.rs:118 (Deposit::vault)

  The IDL declares PDA seeds ["vault", "authority"] for `vault`, but the runtime
  derivation diverges (different seed order, bytes, or omission). External tools
  will derive a different address than the program reads/writes, enabling account
  substitution and state confusion.

  Suggestion:
  Align the `#[account(seeds = ...)]` constraint with the IDL declaration exactly,
  then regenerate the IDL with `anchor build` and redeploy it with `anchor idl fetch`.
```

The analysis works by:
1. Parsing the IDL to extract each account's declared seeds (`kind: const` / `kind: account` / `kind: arg`).
2. Parsing `#[account(seeds = ...)]` constraints from `#[derive(Accounts)]` structs via `syn`.
3. Normalizing both seed lists (constant bytes, account keys, argument paths) and comparing order, bytes, and composition.
4. Flagging any divergence as a `PDA Seed Mismatch` finding with the offending account, location, and a fix suggestion.

## Remediation

1. **Align the code with the IDL (or regenerate the IDL):** the `#[account(seeds = ...)]` constraint must match the IDL-declared seeds exactly — same bytes, same order, same components:

   ```rust
   #[derive(Accounts)]
   pub struct Deposit<'info> {
       #[account(
           mut,
           seeds = [b"vault", authority.key().as_ref()],
           bump = vault.bump
       )]
       pub vault: Account<'info, Vault>,
       pub authority: Signer<'info>,
   }
   ```

2. **Single source of truth:** derive PDAs from one canonical definition. Prefer declaring seeds once in the `#[account(seeds = ...)]` constraint and regenerating the IDL from the source (`anchor build`) — never hand-edit `idl.json` out of sync with the code.

3. **Re-derive in the handler:** for critical accounts, re-derive the PDA inside the instruction body (`Pubkey::find_program_address`) and `require_eq!` it against the passed account's key, so a divergence fails loudly instead of silently using the wrong address.

4. **Verify before deploy:** run the check in CI:

   ```bash
   sat analyze src programs/vault/ --format sarif
   ```

   This emits a `SAT015` (PDA Seed Mismatch) result in `sat-results.sarif`, failing the scan until seeds are aligned.
